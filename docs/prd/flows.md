## 一、端到端主流程

从客户诉求到改进闭环的完整链路，也是平台的"主干道"：

```mermaid
flowchart TD
  S1["客户/业务方提出诉求"] --> S2{"来源渠道"}
  S2 -->|客服热线/企业微信/邮件/开放平台| T1["创建工单"]
  S2 -->|客户经理拜访| T2["记录客户反馈"]
  S2 -->|产品规划/竞品/数据洞察| T3["产品直接立项"]
  S2 -->|监管要求| T4["合规需求登记"]

  T1 --> D1["工单池分诊"]
  D1 --> D2{"分诊判定"}
  D2 -->|咨询| Z1["回复并沉淀 FAQ"]
  D2 -->|重复| Z2["合并到已有工单/需求<br/>客户影响面叠加"]
  D2 -->|不予处理| Z3["说明理由并回复客户"]
  D2 -->|缺陷| B1["创建缺陷并进入缺陷流程"]
  D2 -->|需求| R1["转入统一需求池"]

  T2 --> R1
  T3 --> R1
  T4 --> R1
  Z2 --> R1

  R1 --> R2["需求富化<br/>背景/收益/AC/客户影响面"]
  R2 --> R3{"DoR 就绪度达标?"}
  R3 -->|否| R4["退回补充材料"] --> R2
  R3 -->|是| R5["优先级模型评分"]
  R5 --> R6["需求评审（7 节点）"]
  R6 --> R7{"评审结论"}
  R7 -->|驳回| R8["归档到需求库<br/>可检索可复活"]
  R7 -->|通过| R9["生成阶段计划<br/>设计/编码/联调/测试/发布"]

  R9 --> P1["推送到项目管理"]
  P1 --> P2["拆解为用户故事与任务"]
  P2 --> P3["迭代规划（容量校验）"]
  P3 --> P4{"进入方式"}
  P4 -->|直接指派| P5["指定经办人"]
  P4 -->|投放任务池| P6["自助认领"]
  P5 --> K1["看板拉动式交付"]
  P6 --> K1

  K1 --> C1["创建分支 → 编码 → 提 PR"]
  C1 --> C2["代码评审 + CI"]
  C2 --> C3{"CI 与评审通过?"}
  C3 -->|否| C1
  C3 -->|是| Q1["合并并部署测试环境"]
  Q1 --> Q2["测试执行"]
  Q2 --> Q3{"用例通过且无 P0/P1?"}
  Q3 -->|否| B1
  Q3 -->|是| Q4["产品/业务验收"]
  Q4 --> V1["纳入版本发布清单"]
  V1 --> V2["发布评审与门禁"]
  V2 --> V3{"门禁达标?"}
  V3 -->|否| V4["补测或申请豁免审批"] --> V2
  V3 -->|是| V5["灰度发布"]
  V5 --> V6{"灰度指标正常?"}
  V6 -->|否| V7["回滚"] --> C1
  V6 -->|是| V8["全量上线"]

  V8 --> O1["通知客户经理与关联客户"]
  V8 --> O2["价值复盘（对比预期收益）"]
  V8 --> O3["线上信号监听"]
  O3 --> O4{"出现线上问题?"}
  O4 -->|是| O5["漏测反查分析"]
  O5 --> O6["生成补测用例与改进项"]
  O2 --> O7["迭代/版本复盘"]
  O6 --> O7
  O7 --> O8["行动项闭环跟踪"]
  O8 --> R1
```

## 二、子流程泳道图

### 2.1 工单受理与分诊

```mermaid
flowchart TD
  subgraph C["客户 / 业务方"]
    A1["提出问题或诉求"]
    A9["确认解决"]
  end
  subgraph S["客服一线"]
    B1["创建工单<br/>选择类型自动带出专属字段"]
    B2["首次响应<br/>SLA 时钟启动"]
    B3["一线可解决?"]
    B4["解答并沉淀 FAQ"]
  end
  subgraph P["产品经理（轮值分诊）"]
    C1["进入工单池"]
    C2["系统预判 + 相似度聚类"]
    C3["六类判定"]
    C4["转需求：合并客户影响面"]
    C5["转缺陷：定级并指派"]
  end
  subgraph R["研发 / 测试"]
    D1["缺陷修复流程"]
  end

  A1 --> B1 --> B2 --> B3
  B3 -->|是| B4 --> A9
  B3 -->|否| C1 --> C2 --> C3
  C3 -->|需求| C4
  C3 -->|缺陷| C5 --> D1 --> A9
  C3 -->|重复| C4
  C3 -->|不予处理| B4
  C4 -.->|"需求上线后自动通知"| A9
```

**关键规则**：分诊必须在工单创建后 1 个工作日内完成；相似度 ≥ 0.78 判定为重复并自动合并，合并后客户影响面（呼声数与加权值）叠加到主记录。

### 2.2 需求评审（7 节点）

```mermaid
flowchart LR
  N1["① 需求提出<br/>全员"] --> N2["② 产品初审<br/>产品经理 · SLA 1 天"]
  N2 --> N3["③ 价值评审会<br/>产品总监 · 每周二"]
  N3 --> N4["④ 架构评审<br/>架构师 · SLA 2 天"]

  N6 --> N7["⑦ 价值复盘<br/>上线后 30 天"]
  N2 -.->|驳回| X1["归档库"]
  N3 -.->|补充材料| N1
  N4 -.->|方案不通过| N1
```

| 节点 | 参与人 | 准入 | 准出 | SLA |
| --- | --- | --- | --- | --- |
| ① 需求提出 | 全员 | 标题、描述、来源非空 | 进入需求池 | — |
| ② 产品初审 | 产品经理 | DoR 基础项达标 | 判定真需求 / 驳回 / 补充 | 1 天 |
| ③ 价值评审会 | 产品总监 + 业务方 | 已完成优先级评分 | 逐条投票形成结论 | 每周二固定会议 |
| ④ 架构评审 | 架构师 + 技术负责人 | 技术方案已提交 | 方案通过、依赖已识别 | 2 天 |
| ⑤ 排期评审 | 项目经理 | 已评估人日与容量 | 确定版本与迭代 | 2 天 |
| ⑥ 交付验收 | 产品 + 业务方 | 测试通过 | AC 逐条确认 | 随迭代 |
| ⑦ 价值复盘 | 产品 + 客户经理 | 上线满 30 天 | 对比预期收益，形成结论 | 上线后 30 天 |

### 2.4 看板拉动式交付

```mermaid
flowchart LR
  subgraph LANE["看板列（含 WIP 上限）"]
    L1["待办/任务池<br/>不限"]
    L2["设计中<br/>WIP 3"]
    L3["开发中<br/>WIP 5"]
    L4["代码评审<br/>WIP 3"]
    L5["测试中<br/>WIP 4"]
    L6["待验收<br/>WIP 3"]
    L7["已完成"]
  end
  L1 -->|认领| L2 -->|方案通过| L3 -->|提 PR| L4 -->|合并| L5 -->|用例通过| L6 -->|AC 确认| L7
  L3 -.->|标记阻塞| BK["阻塞计时<br/>超 2 天升级"]
  L4 -.->|评审要求修改| L3
  L5 -.->|用例失败| L3
  BK -.->|解除| L3
```

**拉动而非推送**：下游列出现空位时由下游主动拉取上游"已完成本列"的卡片（卡片显示虚线绿框拉取信号），而不是上游把活推给下游。列超出 WIP 时顶部弹出告警条并提示"停止开始，开始完成"。

## 三、事件驱动的自动流转

平台的状态变更**优先由客观事件驱动**，人工流转是兜底。下图是自动流转规则全景：

```mermaid
flowchart LR
  subgraph GH["GitHub 事件"]
    E1["create branch<br/>feature/REQ-2041-x"]
    E2["pull_request.opened"]
    E3["pull_request_review.submitted"]
    E4["pull_request.merged"]
    E5["workflow_run.completed"]
    E6["release.published"]
  end
  subgraph TEST["测试事件"]
    E7["测试执行完成"]
    E8["缺陷验证通过"]
  end
  subgraph TIME["定时/规则"]
    E9["任务池 4 小时无人认领"]
    E10["PR 创建 4 小时未评审"]
    E11["阶段实际晚于计划 ≥ 1 天"]
    E12["SLA 剩余 30% / 20%"]
    E13["卡片停留超过列阈值"]
  end

  E1 --> A1["工作项 → 开发中"]
  E2 --> A2["工作项 → 代码评审<br/>指派评审人"]
  E3 --> A3["更新评审进度<br/>不通过则退回开发中"]
  E4 --> A4["工作项 → 测试中<br/>触发测试环境部署"]
  E5 --> A5["更新 CI 状态<br/>失败则推送提交人与团队群"]
  E6 --> A6["版本 → 已发布<br/>通知客户经理与关联客户"]
  E7 --> A7["用例全通过且无 P0/P1<br/>→ 待验收"]
  E8 --> A8["缺陷 → 已修复"]
  E9 --> A9["按技能标签推送团队群"]
  E10 --> A10["推送指定评审人"]
  E11 --> A11["阶段标红<br/>推送负责人/项目经理/产品"]
  E12 --> A12["工单/缺陷 SLA 预警与升级"]
  E13 --> A13["卡片老化标记<br/>纳入站会议题"]
```

### 自动流转规则表

| 规则 | 触发事件 | 守卫条件 | 动作 | 可否关闭 |
| --- | --- | --- | --- | --- |
| AF-01 | 创建符合命名约定的分支 | 分支名可解析出工作项编号 | 工作项流转到"开发中"，记录分支 | 可（按团队） |
| AF-02 | PR 创建 | PR 标题或描述含工作项编号 | 流转到"代码评审"，按 CODEOWNERS 指派评审人，启动 4 小时 SLA | 可 |
| AF-03 | PR 评审提交 | — | 更新评审进度；`changes_requested` 时退回"开发中" | 否 |
| AF-04 | PR 合并 | CI 全绿 | 流转到"测试中"，触发测试环境部署，通知测试负责人 | 可 |
| AF-05 | 流水线完成 | — | 更新 CI 状态；失败推送提交人与团队群 | 否 |
| AF-06 | 测试执行完成 | 用例通过率 100% 且无未关闭 P0/P1 | 流转到"待验收"，通知产品 | 可 |
| AF-07 | 版本发布成功 | 门禁通过 | 版本与关联需求流转到"已发布"，通知客户经理与关联客户群 | 否 |
| AF-08 | 任务池超时 | 进入池中 > 4 小时且无人认领 | 按技能匹配推送，最多 3 次后升级项目经理 | 可 |
| AF-09 | 阶段延期 | 实际日期晚于计划 ≥ 1 天 | 标红 + 推送三方 + 计入迭代风险清单 | 否 |
| AF-10 | SLA 预警 | 剩余 30%（工单）/ 20%（缺陷） | 推送处理人与主管；归零自动升级 | 否 |
| AF-11 | 阻塞超时 | 阻塞标记超过 2 天 | 升级项目经理并纳入站会议题 | 可 |
| AF-12 | 生产缺陷关闭后复现 | 30 天内同指纹再次出现 | 自动触发漏测反查流程 | 否 |

**幂等性要求**：所有事件消费以事件 ID 去重，同一事件重复投递不产生重复流转与重复推送。

```mermaid
  WH->>WH: 校验签名 + 事件 ID 去重
  WH->>MQ: 投递事件（至少一次）
  WH-->>GH: 200 OK（3 秒内响应）
  MQ->>SVC: 消费事件
  SVC->>SVC: 解析工作项编号 → 校验状态机守卫
  alt 守卫通过
    SVC->>SVC: 流转到「代码评审」+ 写流转日志
    SVC->>GH: 在 PR 上评论「已关联 STORY-3313，状态已更新」
    SVC->>WC: 推送「PR 待评审」给指定评审人
    WC-->>D: 卡片消息（含"去评审"按钮）
  else 守卫不通过
    SVC->>SVC: 记录未流转原因
    SVC->>WC: 推送提醒（PR 未关联工作项）
  end
```

## 五、异常与边界流程

| 场景 | 处理方式 |
| --- | --- |
| 迭代中插入紧急需求 | 走"插入需求准入规则"：必须由产品总监审批，并明确移出等量点数的原有范围；插入记录计入范围变更率，在迭代复盘中呈现 |
| 需求范围变更 | 已冻结迭代的承诺基线不修改，变更部分单独标记；变更导致的返工工时单独统计 |
| 依赖方延期 | 在依赖图上标记，超过约定 SLA 自动升级到双方负责人；被阻塞方的卡片进入阻塞计时 |
| 生产故障（P0） | 立即拉应急群 + 电话通知；缺陷流程与常规缺陷分离走快速通道；故障恢复后 3 个工作日内完成故障复盘 |
| 发布回滚 | 版本状态流转到"已回滚"，关联需求退回"开发中"，自动创建复盘任务并冻结该版本的后续发布 |
| GitHub / 企业微信不可用 | 自动流转与推送降级：事件进入重试队列，界面提示"自动化暂停"，人工流转入口始终可用 |
| 工时数据缺失（无提交的角色） | 产品、测试、设计等角色以工作项流转事件与日历为主要来源；无法自动推算时提供手工补录入口，标记来源为"手工" |
| 成员离职 | 账号停用而非删除；其名下未完成工作项进入待重新分配队列；历史工时与贡献数据保留 |
