# DevFlow · 研发管理平台高保真原型

面向软件公司研发中心的一体化研发管理系统（对标 PingCode / Jira + Confluence + 服务台 + 效能度量）高保真 HTML 原型。
覆盖 **研发看板、需求管理、工单管理、客户跟踪、产品管理、项目管理、敏捷迭代、测试管理、代码与 CI（GitHub 集成）、智能工时、人员效能与贡献、效能度量、复盘中心、消息与推送、知识库、业务方门户** 十六个模块，
其中 **研发看板** 是团队每天使用频率最高的核心界面，按看板方法（Kanban）与软件研发特性专门设计。
以「星链数科研发中心」为虚构业务场景，数据、流程、指标口径均按真实研发组织的运作方式设计。

核心闭环：**客户/业务方提出（工单·反馈·规划）→ 价值与紧迫性双维度评估 → 阶段排期（设计/编码/提测/上线）→ 研发自助领取任务 → 敏捷迭代交付 →
代码与流水线 → 上线 → 客户回访与价值复盘 → 线上问题反查漏测 → 改进项闭环**，
全过程通过企业微信自动推送进度，对非研发人员开放只读视图，工时依据代码提交自动核算。

原型为**纯静态页面**，零依赖、零构建，双击 `index.html` 即可在浏览器中完整体验（含图表、拖拽、抽屉、弹窗、命令面板）。

## 三、业务设计要点

### 0. 研发看板：团队每天真正在用的那块屏
看板是研发团队使用频率最高的界面，设计目标只有两个：**一眼看懂当前状况，一眼看出哪里卡住了**。

**范围选择器（先选"看什么"，再看板）**：真实使用中很少有人只看一个项目，所以看板顶部固定一条范围栏，四个维度互斥可切：

| 范围维度 | 适用角色与场景 | 看板行为 |
| --- | --- | --- |
| **全部**（默认） | 研发负责人 / VP：看整体流动与瓶颈 | 跨项目聚合，默认按项目分泳道，顶部给出**并行迭代总览**（5 个项目同周期迭代的承诺/完成/完成度/健康度） |
| **按产品线** | 产品负责人：看一条产品线的端到端 | 只保留该产品线的卡片，泳道自动收敛（只剩一组时退化为不分泳道） |
| **按项目** | Scrum Master / 团队：每天站会用 | 附带**迭代下拉**（当前迭代 / 下一迭代 / 全部迭代+Backlog），显示该迭代目标与完成度，恢复严格的 WIP 校验与拖拽流转 |
| **按团队** | 职能负责人：看本团队跨项目的投入 | 按人所属团队过滤，暴露一个团队被几个项目分摊的情况 |

范围选择会**记忆到 localStorage**，也可深链直达：`board.html#scope=prj:PRJ-021`、`board.html#scope=prod:智能风控平台`。项目列表的迭代卡片、项目详情页都有「看板」按钮带范围跳转过来。

跨项目聚合时有三处专门处理，避免出现"看起来像但其实算错了"的数字：
- 卡片补一枚**项目色标**（`#018`/`#021`…），列头下方增加**项目构成条**（各项目在该列的占比）
- WIP 上限是团队级约定，聚合后不能直接相加，所以列头不再比较数值，超限告警改为按**「项目 + 列」分别判定**（如 `#018 开发中（5/4）`），拖拽越界时也只校验卡片所属项目
- 口径分离：迭代承诺点数来自迭代范围（与项目管理页一致），看板卡片点数单独标注"含任务与缺陷，非迭代承诺口径"；「我的看板」把跨项目负载与个人迭代容量对比，直接标出过载百分比

**列 = 真实研发流程**（而不是抽象的"待办/进行中/完成"）：
`待办/任务池 → 设计中 → 开发中 → 代码评审 → 测试中 → 待验收 → 已完成`，每列标注对应研发阶段与故事点合计，「已完成」列可折叠以节省空间。

**结合软件开发特性的卡片设计**——卡片上只放"判断该不该动这张卡"所需的信息：

| 卡片元素 | 解决的问题 |
| --- | --- |
| 顶部类型色条（故事/任务/缺陷/技术债） | 一眼区分工作性质，判断迭代里技术债与缺陷占比是否失衡 |
| 停留天数徽标（≤2 天绿 / 3-4 天黄 / >4 天红） | 卡片**老化**可视化，比"进度百分比"更能暴露真实卡点 |
| 斑马纹左边框 + 阻塞原因 | 阻塞显性化，并自动开始阻塞计时 |
| 分支 / 提交数 / PR / CI 徽标 | 与 GitHub 联动，不用切到代码平台就知道代码进展与构建状态 |
| 用例通过数 / 缺陷数 / AC 确认数 | 测试与验收进展直接体现在卡片上 |
| 虚线绿框「本列已完成，下游可拉取」 | **拉动信号**，让下游主动拉取而不是上游推派 |
| 父需求编号与简称 | 始终能回答"这张卡属于哪条业务价值" |
| 技能标签 + 认领按钮（任务池） | 支撑自助认领，谁能做一目了然 |
| 客户呼声徽标 | 有客户诉求的卡片天然获得更高关注 |

**看板方法的核心机制都落地了**：
- **WIP 在制品限制**：每列可设上限，达到上限变黄、超限整列变红并在顶部弹出告警条（提示"停止开始，开始完成"），拖拽超限时二次提醒。
- **列策略显性化**：点击列头 `?` 查看该列的准入（Ready）与准出（Done）条件，例如"开发中"准出要求"本地自测通过 + 单测覆盖达标 + PR 已提交且 CI 全绿"。
- **泳道**：支持按项目 / 按产品线 / 按需求 / 按优先级 / 按经办人分泳道，P0 自动成为**加急泳道**置顶（不受 WIP 限制但要求 24 小时内闭环）；项目泳道头带迭代、健康度与「只看该项目」下钻。
- **多看板视图**：迭代看板 / 需求看板 / 缺陷看板 / 发布看板 / 我的看板，列与卡片字段按类型自适应。
- **自动化流转**：创建分支 → 开发中；提 PR → 代码评审；PR 合并 → 测试中；用例全通过且无 P0/P1 → 待验收，流转同时推送企业微信。
- **看板度量**（右侧抽屉）：累积流图 CFD、**周期时间散点图**（含 50%/85% 分位线，用于做交付预测而非拍脑袋承诺）、各列平均停留时长、WIP 趋势、阻塞时长 TOP，以及基于流动数据自动生成的**看板健康诊断**。

### 0.5 工单 → 需求 → 工作项：一条完整的价值链路

**工单管理**：列表化管理，支持工单与客户关联；**工单类型可自定义**（类型决定专属字段模板、默认 SLA、默认处理组与可转换目标，如"数据订正"类型必填订正范围/数据依据/授权人/影响金额）。

**工单清洗（分诊台）**：工单先进入工单池，由产品经理轮值分诊，把客户声音转成结构化的需求或缺陷：
- 系统先做相似度聚类与自动预判（置信度 + 预判依据），产品经理只需复核与批量判定
- 六类判定标准公开：**需求**（产品不具备该能力且有持续价值）/ **缺陷**（已有能力但表现与预期不符）/ **重复**（相似度 ≥ 0.78 合并，客户影响面叠加）/ **咨询**（沉淀 FAQ）/ **不予处理**（说明理由并回复客户）
- 相似工单聚类建议可一键"合并并提需求"，合并后价值权重自动叠加

**需求汇总与富化**：工单转化、客户反馈、产品规划、监管合规、数据洞察五类来源汇入**同一个需求池**，每条需求保留来源单号可反查；「清洗与归档」页处理信息不全（AI 从来源工单自动富化背景、收益、验收标准、客户影响面）、疑似重复（合并）、长期无进展（归档到需求库，可随时检索复活），并用 **DoR 就绪度检查**卡住未达标需求。

**转化与分发**：工单和需求都可以**一键推送到项目管理**——选择项目与迭代、拆分为工作项（支持 AI 建议拆分）、选择投放任务池自助认领或按技能指派，阶段计划自动带入；推送后建立双向关联，工作项进度回算需求进度，需求上线自动回写工单并回访客户。

### 0.6 优先级模型：让产品决策公开透明

需求排序不靠"谁嗓门大"，而是一套**可配置、可解释、可追溯**的模型：

| 评审因素 | 默认权重 | 取值方式 |
| --- | --- | --- |
| 业务价值 | 30% | 人工打分 + 收益量化自动校验 |
| 客户权重 | 20% | 自动：客户呼声数 × 客户等级系数 |
| 团队目标支持度 | 15% | 人工：与季度 OKR 对齐度 |
| 紧迫性 | 15% | 自动：承诺日期/合规窗口 + 人工修正 |
| 竞品对标 | 10% | 人工：竞品覆盖度与差距 |
| 风险与合规 | 10% | 规则：合规类自动置 100 |
| 工作量（成本） | 作为除数 | 自动：研发预估人日 |

- **计算方式可自定义**：内置「加权价值 ÷ 工作量系数」「RICE」「WSJF」「纯加权求和」「自定义表达式」五种模板，公式在页面上明文展示
- **实时模拟**：拖动任一因素权重，下方需求排序实时重排并显示"排名变化"，确认后才发布新版本
- **得分可拆解**：每条需求逐因素展示分值、加权价值、工作量系数与最终得分，评审会上直接对着屏幕讨论
- **强制规则优先于算法**：监管合规直接置顶、P0 故障相关插队、战略客户合同承诺 ×1.3、技术债保底 15% 容量
- **版本留痕可回滚**：模型每次调整生成版本（如 v3.2 客户权重 15%→20%），记录调整人与原因，可一键回滚重算

### 0.7 以客户为中心的产品路线图

- **多视角**：同一份路线图支持 **时间轴（季度甘特）/ 版本 / 迭代 / 里程碑 / Now-Next-Later** 五种视图切换，团队按版本和迭代规划任务，管理层看时间轴与里程碑，对外用 Now/Next/Later。
- **关联客户需求**：每个路线图条目显示"N 家客户"徽标，点击即可看到背后的**客户原声与来源工单**（含客户等级），以及关联的需求编号；内部驱动的条目明确标注，避免"自嗨式规划"。
- **对外同步（可控粒度）**：可选择公开哪些条目、面向哪类受众（内部业务方 / 战略客户 / KA / 全部客户）、以什么粒度展示（Now-Next-Later 不含日期 / 按季度 / 精确到发布日），并可生成带水印与访问审计的分享链接（默认 90 天有效）。路线图变更自动同步门户并通知订阅方。
- **门户侧客户视图**：`portal.html` 的「产品路线图」页用 Now / Next / Later 三列呈现，标注「你反馈的」，并回答客户最常问的四个问题（为什么不写具体日期、我的需求为什么在 Later、路线图会变吗、如何影响路线图）。

### 1. 需求管理：多渠道汇聚 + 价值/紧迫双维度评估
- **多渠道统一入口**：工单转化、客户反馈、产品规划、监管合规、数据洞察、竞品对标六类来源统一进池，每条需求都保留来源单号（如 `TK-3821`、`PLAN-Q3-02`）可反查。
- **客户可追溯**：需求关联提出客户与「客户呼声」数量（多少家客户提过同类诉求），客户等级参与影响面加权；上线后自动回访关联客户。
- **双维度评估**：分别评「业务价值」（客户影响面 / 业务收益 / 战略契合 / 信心度）与「研发紧迫性」（时间窗口 / 客户合规压力 / 风险损失 / 依赖阻塞），
  用 **价值 × 紧迫度矩阵** 分为「立即做 / 计划做 / 快速做 / 暂缓」，气泡大小表示投入，避免只看单一分值导致排序失真。
- **分级评审**：P0/P1 走「产品初审 → 架构评审 → 价值评审会 → 排期 → 立项」完整链路，P2 及以下由产品线自决。
- **需求分解**：业务主题（Epic）→ 需求 → 用户故事 → 任务，四级分解树与进度自动汇总。
- **就绪度门禁（DoR）**：验收标准、RICE、技术方案、依赖识别齐备才允许排期。

### 2. 产品管理：路线图与版本发布
- 产品全景（阶段、版本、健康度、业务 KPI、SLA）与**能力成熟度矩阵**。
- 年度路线图甘特：按产品线 × 季度展示举措与里程碑，标注今日线。
- 版本管理：版本内容、就绪度检查清单、发布记录与回滚，发布准入与质量门禁联动。

### 2.5 项目管理四类角色的能力闭环

**产品经理 · 需求拆解与自定义**

- **模板化拆解**：内置「前后端分层 / 按业务流程 / 按技术模块 / 自定义」四种模板，一键生成拆解预览（可逐条编辑标题、点数、归属），支持"AI 再拆一层"到任务级；生成后可直接批量估点并投放任务池。
- **拆解质量检查**：自动校验"所有故事 ≤ 8 点""每个故事可独立交付价值""任务颗粒度 ≤ 3 点""已覆盖全部验收标准""非功能需求已拆出""依赖已识别"，不达标会给出补充建议。
- **自定义状态与属性**：`settings.html` 的工作流页可按**工作项类型分别配置状态机**（需求/用户故事/任务/缺陷/测试用例各自的状态、颜色与流转规则），并提供「工作项类型与颗粒度」配置表——每种类型可自定义图标颜色、层级（L1~L4）、允许的子类型、专属属性、估算单位与是否可自助认领。

**Master · 多版本迭代规划**
- **版本 → 迭代映射**：一眼看清"V3.0 由哪 5 个迭代交付、每个迭代规划了多少点、对应哪些里程碑、发布日是哪天"，并给出风险提示（如"Sprint 26-16 的 13 点大故事若延期将影响 09-30 全量切流"）。
- **多迭代并排规划台**：Backlog + 未来 3 个 Sprint 并排成列，每列显示**容量水位条**（规划量/容量、余量或超出点数）、迭代目标、关联里程碑；卡片可**拖拽跨迭代移动**，超容量实时告警并支持"自动调平"。
- **就绪度拦截**：未通过 DoR 的工作项拖入迭代会被拦截并提示原因，从源头避免"边做边想"。
- **迭代优先排序**：迭代列表带优先级、目标、里程碑对齐与水位，Master 可对多个迭代统一排序与调整。
- **规划风险提示**：大故事未拆分、未就绪项、水位过高、跨团队依赖，四类风险自动列出。

**研发工程师 · 多任务管理**
- `mywork.html` 新增「我的任务（跨项目）」：跨项目/跨迭代聚合本人全部任务，按优先级/项目/截止排序。
- 每张任务卡直接展示**优先级、状态、CI 状态、分支、工时进度、截止时间、阻塞原因**；展开即可看到**子任务清单并勾选**，勾选后进度自动重算，也可现场添加子任务、逐条登记工时。
- 底部实时显示"合计点数 vs 本迭代容量"，超载时提示应转出多少点；右侧「可认领任务」按技能匹配推荐，与任务池打通。
- 另有 `board.html` 的「我的看板」提供个人视角的看板视图。

**管理者 · 项目资源分配**
- `project.html` 的「资源排期与容量」页：**可用容量 = 基准容量 − 请假/公休 − 会议与协作 − 运维值班 − 缓冲**，先算清可用容量再做排期承诺。
- **成员 × 周排期表**：每格显示该成员当周的总分配率与各项目占比，按 ≤70% / 71~90% / 91~100% / >100% 四档着色，休假单独标灰；点击格子可直接调整排期。
- **冲突与超载检测**：自动识别"同一人同期被多个项目占用超容量""休假与发布窗口重叠"等问题，并给出可执行建议（转给谁、降到多少、推迟到什么时候）与"采纳建议"一键调平。
- **快速排期**：选择成员、项目、时间段与投入比例，实时做容量校验（如"何俊已排 116%，再排 80% 将达 196%"）并展示排期后对各项目与个人负载的影响。

### 5.6 敏捷开发：仪式、估算与多团队协同
- 全中心统一 2 周迭代节奏，迭代节奏总览可一屏看到 6 个团队的当前/下期迭代与发布窗口。
- **每日站会**支持异步同步，「昨天完成」由代码提交与工作项流转自动预填，阻塞项自动汇总并 @ 责任人。
- **规划扑克估算**：多人出牌、分歧提示、共识采纳，并统计不同点数区间的估算准确度（13 点以上准确度显著下降 → 强制拆分）。
- **迭代健康**：速率与承诺达成、范围蔓延、缺陷注入率、迭代健康雷达、敏捷成熟度分级（L1~L5）。
- **跨团队依赖**：依赖地图 + 依赖清单（期望时间 vs 提供方计划 + 阻塞状态 + 协调人）。

### 5.7 复盘：让每次交付沉淀经验
- **迭代回顾**：Keep / Problem / Puzzle / Action 四象限看板，支持匿名反馈与投票，行动项自动生成任务并纳入下个迭代。
- **需求价值复盘**：上线 30 天后自动进入复盘队列，按上线前约定的度量口径对照「预期收益 vs 实际达成」，结合自动核算的投入成本给出 ROI 与结论（超预期 / 达成 / 部分达成 / 未达成）。
- **故障复盘**：时间线（发现/响应/定位/恢复各段耗时）+ 5 Why 根因 + 改进措施，根因分类聚合识别系统性问题。
- **改进项闭环**：所有复盘产出的改进项统一跟踪，闭环率、平均闭环时长、重复出现问题作为管理指标。

### 5.8 智能工时：根据代码提交自动反馈
- **数据来源**：Git 提交（时间聚类 + 代码当量）、PR 评审、CI 失败重跑、工作项状态流转、会议日历。
- **推算模型**：编码工时 = 提交时间聚类跨度 × 0.8 + 代码当量 ÷ 每小时基准当量；叠加评审、联调、会议工时，按 0.5 小时取整，成员可 ±30% 调整后确认。
- **自动归集**：提交信息中的 `[REQ-2041]` / 分支名 `feature/REQ-xxxx` 决定工时归到哪条需求，无编号的按分支所属项目分摊；归集率与未归集提交单独跟踪并可批量提醒。
- **直接产出**：需求实际投入与成本自动核算 → 供价值复盘计算 ROI；人效与成本度量不再依赖手工填报。
- **使用原则**：明确不作为个人绩效考核依据，不采集代码内容与击键行为，个人明细仅本人与直属主管可见。

### 5.9 业务方门户：让非研发人员看得懂进度
- 独立的浅色轻量布局与非技术化措辞（用「研发周期」而非 Sprint），只读、免培训。
- **需求进度**：六阶段可视化步骤条（已提交 → 需求评审 → 已排期 → 研发中 → 测试中 → 已上线）+ 预计上线时间 + 最近进展 + 价值/紧急评估结果 + 催办与补充说明入口。
- **我的工单**：状态、处理人、预计解决时间、服务时效承诺与自助 FAQ。
- **版本发布**：近期版本发布计划时间线，与自己相关的需求高亮，可订阅发布通知。
- **研发进展**：本期在做什么、下期计划、整体交付情况与研发团队公告。

### 5.10 任务自助认领：从"派活"到"接活"
- 项目经理只负责拆分与排优先级，任务先进入**任务池**，不逐一指派。
- 任务带技能标签，系统按「优先级 × 技能匹配度」排序，匹配度 ≥ 60% 自动推送到个人企业微信，成员一键认领。
- **认领时校验容量**：认领后总点数超过个人容量 110% 需负责人确认，避免过载。
- **兜底机制**：P0 任务 2 小时无人认领自动指派给最匹配者，普通任务 8 小时无人认领由技术负责人指派；开始前 24 小时内可释放回任务池。
- 认领后自动进入个人看板并开始计时，**进度由代码提交自动回填**，无需手工更新。当前自助认领率 78%，认领任务的按时完成率比指派任务高 6pt。

### 5.11 企业微信自动推送：进度找人，而不是人找进度
- **事件驱动**：24 条推送规则覆盖需求全流程（提交 → 评审 → 设计 → 编码 → 提测 → 上线 → 回访 → 复盘）、迭代（站会/日报/偏离预警）、代码与 CI、缺陷与 SLA、工单与客户承诺、工时与复盘。
- **企业微信原生形态**：模板卡片 + 交互按钮，可直接在会话内完成认领、确认、评审跳转；页面内提供 14 种消息的卡片预览。
- **精准与克制**：同类消息 5 分钟合并、每人每日上限、连续 3 次未点击自动降级、@全员仅限 P0；免打扰时段与休假代理，P0 与生产故障强制触达。
- **升级策略**：30 分钟未响应推团队群 → 2 小时升级技术负责人 → 4 小时升级部门负责人；P0 15 分钟直达总裁并电话提醒。
- **可度量**：送达率、已读率、点击率、响应时长全量记录，每月自动评估消息价值，低点击率规则建议关停，避免消息疲劳。

### 5.12 需求阶段排期：什么时候设计、编码、提测、完成
- 每条需求维护 **5 个阶段**（需求设计 → 编码开发 → 联调自测 → 测试验收 → 发布上线）的计划起止时间，其中 **开始设计 / 开始编码 / 计划提测 / 计划上线** 为四个关键节点。
- 计划可由工作量按模板自动推算；**实际日期由工作项状态流转与代码提交自动回填**，无需人工登记。
- 需求池提供「阶段排期」甘特视图：一屏看到所有需求的阶段分布、当前阶段进度、延期标红与今日线。
- **延期自动预警**：任一阶段实际晚于计划 ≥ 1 天，自动推送负责人、项目经理与产品总监，并给出影响分析（是否顺延提测/上线）。
- 各阶段计划 vs 实际平均时长持续统计（当前编码阶段平均超期 3.4 天），用于修正后续排期模型。

### 5.13 漏测自动化评估：用线上问题反查测试有效性
测试质量不能只看"执行了多少用例、通过率多少"，关键是**拦住了多少问题、漏了什么**。系统以线上工单与生产缺陷为输入，自动反查：

1. **采集线上信号**：生产工单、生产缺陷、告警事件。
2. **聚类去重**：文本相似度 + 报错指纹，把同一问题的多条工单合并（相似度阈值 0.78）。
3. **关联需求与模块**：按堆栈代码路径反查最近变更的需求 / PR（命中率 84%）。
4. **检索用例覆盖**：通过需求-用例矩阵与语义相似度（阈值 0.72）判断是否存在对应用例。
5. **判定漏测类型**：

| 反查结果 | 判定类型 | 责任环节 | 自动动作 |
| --- | --- | --- | --- |
| 无匹配用例 | 用例缺失（场景遗漏） | 测试设计 | 生成补测用例 + 用例评审改进项 |
| 有用例但本轮未执行 | 执行遗漏（范围裁剪不当） | 测试执行 | 纳入回归基线、标记必测 |
| 有用例且执行通过 | 用例失效（断言/数据不足） | 测试设计 | 优化用例断言与测试数据 |
| 用例覆盖但环境不具备 | 环境差异 | 测试环境/SRE | 补充预发验证与影子数据 |
| 需求未定义该场景 | 需求遗漏（非测试责任） | 需求分析 | 补充验收标准 + 需求评审改进项 |
| 第三方/生产配置引发 | 外部因素（非测试责任） | 运维/供应商 | 纳入变更评审与监控告警 |

6. **闭环**：自动创建补测用例任务、生成复盘改进项，并推送漏测周报；自动判定结果由测试经理每周复核，纠正样本回流校准（当前自动判定准确率 92%）。

配套的**测试有效性指标**：漏测率、缺陷探测率 DDP（各阶段拦截占比）、用例有效性（曾发现缺陷的用例占比 34%）、僵尸用例比例（28%）、场景覆盖缺口清单。
这套机制的价值在于把"漏测"从事后追责变成可自动识别、可归因、可补齐的工程问题——例如本次识别出"大数据量批处理场景"是漏测集中区，直接产出 4 条补测用例并推动纳入 DoD。

### 5.14 人员效能与产品贡献：能看到每个人，但不用来简单排名
研发中心需要回答两个具体问题：**每个人的效能怎么样**、**每个产品是谁做出来的**。这两个问题都在 `people.html` 里闭环，数据全部由系统自动采集（工作项、GitHub、流水线、测试、工时、知识库），不新增任何填报。

**个人效能画像（六维，避免单指标误导）**

| 维度 | 权重 | 主要构成 | 数据来源 |
| --- | --- | --- | --- |
| 交付产出 | 30% | 已验收故事点、交付需求数（按复杂度加权） | 工作项 + 迭代验收 |
| 交付质量 | 25% | 缺陷密度、一次通过率、返工率、逃逸缺陷 | 缺陷系统 + 测试管理 + 漏测分析 |
| 协作响应 | 20% | PR 评审响应时长与有效意见、阻塞协助、跨团队支持 | GitHub + 看板阻塞记录 |
| 技术贡献 | 15% | 架构改进、组件复用、技术债偿还、性能优化 | 代码分析 + 技术债台账 |
| 知识与带人 | 10% | 文档、分享、结对、新人辅导、复盘输出 | 知识库 + 复盘中心 |
| 交付稳定 | 修正 ±5% | 承诺达成率、按时交付率、计划偏差 | 阶段排期 + 迭代承诺 |

每个人的画像包含：雷达图（对比团队中位与同职级）、关键指标卡、效能趋势（近 6 个月，用趋势而非单点评判）、**贡献事实清单**（每一分都能下钻到具体需求/缺陷/评审/文档，可申诉补充）、主管视角建议（优势 / 风险 / 待提升 / 发展建议）。

**产品贡献率（双视角）**

```
加权贡献 = 有效工时 40%（智能工时按 commit 归集）
         + 交付故事点 30%（已验收）
         + 需求业务价值分 30%（价值评估分 × 参与度）

个人视角：该成员各产品占其自身贡献的比例（合计 100%）
产品视角：该产品各成员的贡献占比（合计 ≤ 100%，余量为其他成员）
```

「成员 × 产品」热力矩阵可同时读两个方向：横看一个人的精力分配是否聚焦、纵看一个产品是否过度依赖某个人。系统按 **单人贡献率 > 40%** 自动识别**单点依赖风险**，并区分产品级与模块级（例如某人产品级贡献率仅 18% 属健康，但「路由与清结算」模块级达 52%，仍是单点）。

**人才识别**：产出 × 质量四象限（骨干 / 高质量待提效 / 高产出待提质 / 需要帮助，阈值取团队中位数动态计算，气泡大小为投入人日）、团队效能分布箱线图、骨干与高潜名单、需要帮助名单与帮扶措施、人力配置建议。

**治理原则（写进产品，不只是说说）**
- 不使用代码行数/提交次数直接排名，代码当量仅作参考项并按语言与复杂度加权
- 分角色归一化（研发/测试/产品/架构只与同角色同职级比较）
- 质量与产出必须同时看：高产出但缺陷密度超阈值不进入高绩效区间
- 异常行为检测（拆分提交、无意义格式化、刷评审）
- 禁止单月定论：至少 3 个月趋势 + 主管校准才可用于人才决策
- 可见范围分级：本人可见自己全部数据并可申诉，HRBP 不可见原始代码数据
- 校准流程：月度主管审阅 → 季度团队校准会 → 半年人才盘点

### 6. 效能度量：四层指标体系
| 层级 | 指标 |
| --- | --- |
| 交付效率 | 需求交付周期（含等待分解）、吞吐量、按时交付率、WIP、流动效率 |
| 交付质量 | 缺陷密度、缺陷逃逸率、一次通过率、线上故障与 MTTR |
| 交付能力 | DORA：部署频率、变更前置时间、变更失败率、服务恢复时间（含行业对标） |
| 组织人效 | 人均交付、有效投入率、故事点成本、负载与加班健康预警 |

度量口径遵循「**用于发现系统性瓶颈，而非考核个人**」原则，效能报告支持 AI 自动生成结论与改进举措。

### 7. 知识库
空间 → 目录 → 页面三级结构，支持模板、版本、审批、评论、目录导航、权限与复审周期；与需求 / 项目 / 缺陷双向关联。

## 六、从原型到产品的落地建议

1. **技术选型**：前端 React/Vue + TypeScript + 组件库（可直接复用本原型的 Design Token）；图表切换为 ECharts；后端建议领域拆分为 `需求域 / 项目域 / 测试域 / 集成域 / 度量域`。
2. **数据模型**：以「工作项（WorkItem）」为统一抽象，通过类型（需求 / 故事 / 任务 / 缺陷 / 用例 / 工单）+ 可配置字段 + 可配置状态机实现多形态，避免为每类对象建独立模型；
   客户（Customer）作为独立主数据，与工单、需求、承诺建立多对多关联，是「客户影响面」计算与对外门户鉴权的基础。
3. **集成优先级**：GitHub（代码 / PR / Actions）→ 制品与部署 → 监控告警 → IM 通知 → 历史系统（Jira/TAPD）数据迁移。
4. **度量落地**：先打通事件采集（工作项状态变更、Git 事件、流水线事件、部署事件），再构建指标口径层，最后做可视化，避免口径不一致导致数据不被信任。
5. **智能工时落地要点**：先只做「推算 + 人工确认」不做强制，用 2~3 个迭代校准模型参数（聚类窗口、基准当量）；
   明确工时不用于个人考核，否则会诱发刷提交等反向行为；归集依赖提交规范，需在 CI 中加编号校验。
6. **对外门户的边界**：业务方门户只读，且做字段级脱敏（不暴露人力成本、内部评分细节与技术缺陷详情）；
   客户侧共享链接建议设置有效期与水印。
7. **任务认领落地要点**：先在 1~2 个成熟团队试点，配套技能标签体系与容量口径；必须保留兜底指派，否则难任务会长期无人认领。
8. **漏测评估落地要点**：先打通「工单 → 缺陷 → 需求 → 用例」的关联链路（缺一环则无法自动反查），初期以人工复核为主，
   用 2~3 个月样本校准匹配阈值；判定结果用于改进用例与流程，不建议直接与个人考核挂钩。
9. **人员效能落地要点**：这是最容易做坏的模块。建议先只对**主管开放团队视图**，个人画像先给本人看，跑 1~2 个季度让大家确认数据准确后再用于人才盘点；
   一定要保留"事实清单 + 申诉"，否则任何自动评分都会失去信任；产品贡献率优先用于**人力配置与单点依赖治理**，而非绩效分配。
10. **推行节奏**：单产品线试点（建议支付网关）→ 固化流程模板与门禁 → 全中心推广 → 度量驱动持续改进。
